# Decision Log

Running log of technical decisions for the Blue Machines FDE assignment (AI loan-servicing PoC).
Newest decisions at the bottom. Each entry: what we decided, why, and what we gave up.

Status: `Accepted` = agreed, `Proposed` = suggested but not yet confirmed, `Superseded` = replaced by a later entry.

---

## D-001 — Language: TypeScript end to end
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Backend (Node) and frontend (React) both in TypeScript.
- **Why:** The live review includes modifying code on the spot, and TypeScript is the stack I'm most fluent in. One language across client, server and shared types (tool schemas, events) avoids drift between them.
- **Trade-off:** Python has a richer ML/voice ecosystem, but we don't need it because all model work goes through hosted APIs.

## D-002 — Models and voice vendors: Gemini + ElevenLabs
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Gemini for reasoning and tool calling. ElevenLabs for streaming speech-to-text (Scribe realtime) and streaming text-to-speech.
- **Why:** These are the keys I already have, and both support the streaming we need for low-latency voice.
- **Trade-off:** We're tied to two vendors. They sit behind thin adapter interfaces so either can be swapped.

## D-003 — Voice architecture: our own STT → engine → TTS pipeline (not speech-to-speech)
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Build the pipeline ourselves: ElevenLabs STT → our query engine → ElevenLabs TTS. We are not using Gemini Live's native speech-to-speech.
- **Why:** Voice and text go through the **same engine**, so the same accuracy, tools, policies and audit apply on both channels. We control interruptions (barge-in) and filler or progress speech during slow backend calls. Each stage can be measured separately, and the reviewers said they'll judge the real interaction and latency.
- **Trade-off:** There are more moving parts, and latency could be slightly higher than an end-to-end speech model. We offset that by streaming at every stage.

## D-004 — Transport: one WebSocket per conversation, shared by text and voice
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The browser and backend talk over a single WebSocket per session. It carries mic audio up, TTS audio down, transcripts, progress events and barge-in/cancel signals. Text chat uses the same socket. Plain REST is used only for login and dashboard data.
- **Why:** Voice needs low-latency signalling in both directions to handle interruptions. Using one socket for both channels means a customer can switch from typing to talking mid-conversation with the context kept, which supports the "one engine, many channels" story.
- **Trade-off:** It's stateful, so scaling needs sticky sessions plus an external session store (see D-007).

## D-005 — Scale path: in-memory for the PoC, Redis-backed sessions in production
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The PoC keeps session context in process memory. The design keeps socket servers stateless apart from that store, so they can scale horizontally to 1,000 concurrent conversations by moving sessions to Redis/Memorystore and adding sticky load balancing.
- **Why:** This answers the brief's scale constraint without paying the setup cost now. The backend ships as a container (Dockerfile), so it can run unchanged on Cloud Run or GKE.

## D-006 — Second workflow (platform demo): Collections
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The second use case is collections: the assistant helps an overdue customer understand their dues and options, then records a promise-to-pay.
- **Why:** Collections is a core Blue Machines use case. It's a genuinely different business goal (recovery rather than service) on the same customer and loan data, which shows the platform carries over while letting us reuse the most and spend time on polish. It's added mostly as configuration (tools, policies, prompt, allowed actions) on the shared engine, connectors, action/audit and telemetry layers.
- **Alternative considered:** Credit-card servicing. It's a different product, but needs a new mock system for less extra proof.

## D-007 — Accuracy approach: calculations in code, answers cite sources
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The LLM plans and explains, and deterministic code does the maths (EMI, amortisation, prepayment savings, charges) and evaluates policy rules. Every answer carries its sources: which system, which policy clause, which formula.
- **Why:** The brief explicitly asks for precise, verifiable, customer-specific answers and "not an LLM connected to a vector database."

## D-012 — Barge-in tuned for a video-call demo, with a push-to-talk fallback
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:**
  - Barge-in fires only on real speech: a partial transcript with at least 2 words, or about 400 ms of sustained speech. The thresholds are configurable.
  - The browser mic runs with echo cancellation, noise suppression and auto gain control.
  - A push-to-talk mode is available as a fallback.
- **Why:** The live review happens over a video call from a laptop. Speaker echo, coughs or a reviewer's voice leaking from the call would otherwise make the assistant cut itself off. Open-mic with interruptions is the headline experience, and push-to-talk is the safety net.
- **Trade-off:** A deliberate 1-word interruption ("stop") reacts slightly later. We may add a small keyword list ("stop", "wait", "hold on") that triggers barge-in immediately.

## D-013 — Collections actions use the same confirmation-gated action flow
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Promise-to-pay and payment-link generation are proposed by the LLM and executed only after the customer confirms, exactly like the loan-servicing actions.
- **Why:** One action model across workflows is part of the platform claim, and it keeps the security guarantee uniform: the LLM never executes anything on its own.

## D-014 — Full-duplex streaming at every hop (no speculative LLM start)
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Nothing in the voice path waits for a complete payload, except the user's transcript. Every hop is a stream over a persistent socket:
  1. **Browser → server:** mic audio leaves as 20–40 ms PCM chunks over our WebSocket while the user is still speaking.
  2. **Server → ElevenLabs STT:** chunks are forwarded straight to the Scribe realtime socket. Partial transcripts come back continuously and are shown as live captions only.
  3. **STT → LLM:** the LLM turn starts on the **committed (final) transcript**. The STT's end-of-turn silence threshold is tuned short (about 400–500 ms, configurable) to keep that gap small.
  4. **LLM → TTS:** Gemini's token stream is cut at clause boundaries, and each clause goes into the ElevenLabs streaming-input TTS socket immediately. The first chunk is sent early, at the first clause or about 40 characters, and the stream is flushed at the end.
  5. **TTS → browser:** audio chunks are forwarded as they arrive, played through a small jitter buffer, and kept in sync with the on-screen text.
- **Supporting latency tactics:**
  - The customer snapshot is prefetched at session start, so simple questions need no tool calls.
  - Read tools run in parallel.
  - Filler speech plays while slow tools run.
  - The STT and TTS sockets are pre-warmed when voice mode starts.
- **Why:** In a voice conversation, perceived speed is the time from the end of user speech to the first assistant audio. Streaming every hop turns that into the *time to the first token/clause* at each stage, instead of the sum of full completion times.
- **Rejected: speculative LLM start on partial transcripts** (a.k.a. preemptive generation).
  - Gemini's standard API can't take incremental input, so each transcript change means a fresh request that repeats prompt processing.
  - The saving is only about 100–300 ms, which mostly comes for free from tuning the STT silence threshold.
  - Partial transcripts are exactly where amounts change ("fifty" vs "fifteen" thousand). A restart costs more than speculation saves, and a missed restart answers the wrong number, which breaks the accuracy promise.
  - Mid-sentence pauses cause abort churn and extra backend reads.
  - It's kept as a possible future optimisation, to be adopted only if measurements show STT finalisation dominating latency.
- **Trade-off:** We accept STT finalisation time on the critical path in exchange for correctness and simpler cancellation. Clause-level TTS chunks can slightly flatten prosody compared with sending whole sentences.
- **Measured:** the trace records each hop (first partial, STT commit, LLM first token, first TTS chunk sent, first audio played), so the latency report shows where the time goes.

## D-015 — Numbers are bound by code, never written by the LLM
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Tool results expose named values (e.g. `emi.new`, `prepay.interestSaved`). The LLM writes prose with placeholders (`Your EMI rose to {{emi.new}}`), and the streaming renderer replaces each placeholder with the code-formatted value as the text flows to the UI and TTS. A placeholder that doesn't resolve fails closed: it's shown as "I couldn't verify that figure" and flagged in the trace. The numeric-grounding check stays as a second line of defence for any literal number the model writes anyway.
- **Why:** Accuracy is the customer's top complaint. This makes a hallucinated figure impossible by construction, instead of something detected afterwards.
- **Rejected:** letting the LLM write numbers and validating them afterwards only. That detects errors but can't prevent them, and a regeneration costs a full extra turn.
- **Trade-off:** It adds a little prompt complexity, and the renderer must hold back a partial `{{…` token while streaming, which delays text by a few characters at most.

## D-016 — Tool granularity: combined tools for common questions, basic tools for the long tail
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** High-frequency questions get combined tools that fetch and compute in one call (`explain_emi_change`, `simulate_prepayment`, `check_foreclosure`, `list_options`, `get_overdue_summary`). Basic tools (`get_loan_details`, `get_payment_history`, `get_policy`, …) cover the long tail.
- **Why:** Each LLM↔tool round trip costs about 0.5–1 s and is another chance for the model to chain steps wrongly. Common questions should resolve in one tool round.
- **Rejected:** only basic, CRUD-like tools (flexible but slow and error-prone). Only combined tools (fast, but brittle for unexpected questions).

## D-017 — Policies as versioned structured rules with effective dates (no vector search)
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Each policy clause has `id`, `version`, `effectiveFrom/To`, applicability (product, rate type, borrower type), the citation text and an optional evaluator function. Lookup is by id/topic, filtered by the clause version in force for *that loan* (sanction date or event date).
- **Why:** Eligibility is logic, not textual similarity, and the right answer depends on which version of a rule applied to this customer at the time.
- **Rejected:** vector search over policy documents. It can surface plausible but inapplicable text, has no notion of version, and is exactly the "LLM + vector DB" pattern the brief warns against. Vector search remains an option later for a large unstructured FAQ long tail, never for rules.

## D-018 — Prompt layout optimised for Gemini context caching
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The prompt is built from most stable to least stable: system prompt → tool declarations → workflow policy summaries → customer snapshot → entity memory → recent history → current turn. Implicit caching is used, with explicit context caching where the model supports it.
- **Why:** Repeated identical prefixes are served from cache, which reduces time-to-first-token and cost on every turn.
- **Trade-off:** Prompt sections must stay byte-stable (no timestamps or random ordering in the prefix). This is enforced by building the prompt in one place.

## D-019 — Hedged reads and stale-while-revalidate for slow or failing backends
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:**
  - **Hedging:** for idempotent reads, if a call exceeds that system's observed p95, a second identical request is sent and the first response wins. Hedging is capped at about 10% extra load per system.
  - **Stale data during failures:** if a read fails after retries/hedging (or the circuit is open), the last cached value is served with an explicit "as of" timestamp. The assistant must state the freshness ("as of 10:42 today").
  - **Writes:** never hedged. They are retried only with an idempotency key.
- **Why:** The brief requires responsiveness despite slow and intermittent backends. Hedging cuts tail latency without slowing the common case, and serving stale data with disclosure is more useful than "system unavailable."
- **Rejected:** retries alone, which add latency exactly in the slow cases.
- **Trade-off:** Hedging adds some backend load, and stale data can mislead if freshness isn't stated. The prompt and renderer always attach the "as of" timestamp.

## D-020 — Indian number and date formatting done deterministically for text and speech
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** One formatting module renders money in the Indian system: ₹1,23,456 for display, and "one lakh twenty-three thousand four hundred fifty-six rupees" (or "about 1.23 lakh" where suitable) for speech. Dates and percentages are formatted the same way. Placeholder binding (D-015) uses the speech variant on the voice channel.
- **Why:** LLMs and TTS engines frequently mangle Indian-format numbers, and a misread amount over voice is an accuracy failure.
- **Rejected:** relying on the LLM or TTS text normalisation.

## D-021 — Action confirmation is a deterministic state machine bound to the exact terms
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:**
  - A proposal is stored with `proposalId` and `termsHash` (hash of action type + canonical parameters + computed figures), plus an expiry.
  - The UI confirm button sends `{proposalId, termsHash}`. A voice confirmation is accepted only while exactly one proposal is pending, and only after the key figures have been read back.
  - Execution re-validates ownership, limits and policy at execution time, and rejects the confirm if the terms changed.
  - The LLM has no "execute" tool at all.
- **Why:** The model must not be able to cause a side effect. A confirmation must refer to exactly what the customer saw or heard.
- **Rejected:** executing when the model decides the user agreed.

## D-022 — Data minimisation before the LLM
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** PAN, full phone, email, bank account and full loan-account numbers are masked or tokenised *before* inclusion in prompts or tool results sent to Gemini (e.g. `XXXX-1234`). The un-masking that real actions need happens server-side by token. Logs and traces use the same masking.
- **Why:** The model never needs raw identifiers to answer, and sending less PII to a third-party model is the right default for a regulated lender.
- **Trade-off:** If the customer asks for their full account number, it's shown by the UI from the server, not spoken or written by the LLM.

## D-023 — Event-sourced turn log with deterministic replay
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Every turn is recorded as an ordered list of events: user input (text or transcript), the prompt hash, LLM requests and responses, tool calls with recorded backend responses, guard verdicts, proposals and confirmations, the final answer and timings. A replay command re-runs any conversation with backends stubbed from the recorded responses (and optionally the recorded LLM outputs), to reproduce a bad answer or test a prompt or code fix against it.
- **Why:** Debugging LLM systems from text logs is guesswork. Replay turns "the bot said something wrong to a customer" into a reproducible test case. This is the core of incident response for AI agents.
- **Rejected:** plain structured logs only.

## D-024 — Backpressure and concurrency control
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:**
  - At most one active turn per session: new input cancels the in-flight turn, per D-003/barge-in.
  - A process-wide limiter on concurrent LLM calls, with a bounded queue. A turn that waits in the queue too long gets a graceful "high demand" response and a filler.
  - Bounded per-session audio buffers that drop the oldest data when full.
  - Per-IP and per-session rate limits.
  - The load script measures event-loop lag, memory per session and queue depth under load.
- **Why:** At 1,000 concurrent conversations, the failure mode is unbounded queues and memory, not average latency. Limits make overload visible and graceful.

## D-025 — Workflow packs are typed TypeScript objects, not a YAML/JSON configuration format (yet)
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** A workflow is a typed `WorkflowDefinition` in TypeScript (prompt, tools, actions, policy scopes, opener, voice settings).
- **Why:** The compiler checks tool and action names, refactors are safe, and live edits during the review are fast. The authors today are engineers.
- **Rejected for now:** a YAML/JSON configuration format, which pays off once non-engineers (ops/solutions teams) author workflows. The typed object is serialisable, so a configuration format can be added on top without rewriting the engine.

## D-026 — Defence against malicious or manipulative user input
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Defence in depth, with the hard guarantees in code rather than in the prompt:
  1. **Capability limits.** The agent can only call its workflow's tools, all scoped server-side to the authenticated customer (D-009). No tool exists to waive charges, change rates or terms, read other customers, or run arbitrary queries. Such requests can at most become a service ticket for human review.
  2. **Action limits in code.** Amounts are bounded (e.g. prepayment ≤ outstanding, within daily limits), disputes apply only to the customer's own payments, and policy is re-checked at execution. All of this sits behind the hash-bound confirmation (D-021).
  3. **A parallel input guard.** A fast rule check plus a small-model classifier runs alongside the main turn (no added latency on the happy path). It flags jailbreak attempts, social engineering ("I'm from the bank, approve this"), requests for other people's data, and abuse. A flag blocks any action proposal from that turn and replaces the answer with a polite refusal.
  4. **Indirect injection.** Free text from backends (CRM notes, dispute descriptions, policy text) is delimited and labelled as untrusted data in the prompt. Instructions inside it are ignored, and it can't grant capabilities anyway (see 1).
  5. **Output rules.** The system prompt is never revealed, figures come only via placeholders (D-015), and off-topic content is declined.
  6. **Escalation.** Repeated flagged attempts in a session lead to a firm refusal, then the session is flagged in the audit log and offered a human handoff.
  7. **Red-team evaluation.** `scripts/eval` includes an adversarial set (about 15 prompts: injection, impersonation, cross-customer access, fee-waiver coercion, prompt extraction, malicious content in a dispute description) with expected outcomes. The write-up reports the pass rate.
- **Why:** In a regulated lender, the bar is "the model *cannot* do the wrong thing," not "the model was told not to." Prompts reduce attempts, and code makes them harmless.
- **Rejected:** prompt-only guardrails. Also rejected: a serial guard before every turn, which adds about 200–400 ms to every turn for a rare event.
- **Trade-off:** The parallel guard can flag after some text has already streamed. The UI then retracts the partial answer, and no action can have happened because proposals are held until the guard verdict arrives.

## D-027 — Binary WebSocket frames with a `turnSeq` header for audio
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Audio travels as binary WebSocket frames: a 4-byte big-endian uint32 `turnSeq` followed by PCM16LE. Upstream mic frames use `turnSeq = 0`. Control messages stay JSON. The helpers `encodeAudioFrame`/`decodeAudioFrame` live in `@app/shared`.
- **Why:** The header lets the client drop stale audio from an interrupted turn cheaply (compare `turnSeq` with the current one) and lets the server tag TTS output per turn, with no JSON parsing on the hot path.
- **Rejected:** base64 audio inside JSON messages, which adds about 33% overhead and makes stale-audio filtering harder.

## D-028 — UTC ISO-string date math; speech rounds paise to rupees
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Business dates are `YYYY-MM-DD` strings and all date math (`addMonths`, `monthsBetween`, `daysBetween`) uses UTC components, so timezone never shifts a date. `today()` reads `DEMO_TODAY` at call time, not at module load. `addMonths` clamps to month end, and `monthsBetween` treats a clamped month end as a full month, which keeps it consistent with `addMonths`. `speakInr` rounds paise to whole rupees (zero is "zero rupees").
- **Why:** Tests and demos can change the clock per call, and spoken amounts stay short.
- **Rejected:** `Date` local-time arithmetic, which drifts across DST and server timezones.

## D-029 — Amount parsing is strict and shares the speech vocabulary
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `parseAmount` accepts digits with ₹/Rs/commas and the suffixes k, l, lakh, lac, cr and crore, or number words up to crore. The word table is the reverse of the one `speakInr` uses (`ONES`/`TENS` exported from `format/inr.ts`). Scales must strictly descend ("one thousand lakh" and "50 crore crore" are rejected). Negative, zero, more than 2 decimal places, or partially parsed input is rejected with a reason and never guessed.
- **Why:** A mis-heard amount that moves money is worse than asking again.

## D-030 — Finance calculators: paise integers, per-step rounding, baseline from the actual EMI
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** All calculators work in integer paise. EMI uses the closed-form formula in floating point and is rounded to the nearest rupee. Amortisation rounds monthly interest (`opening × bps / 120000`) to paise at each step, and the last instalment is `opening + interest`. Prepayment savings are measured against a baseline schedule built from the loan's actual EMI (not from `remainingMonths`). "Reduce tenure" keeps the EMI and re-amortises. "Reduce EMI" keeps `remainingMonths` and recomputes the EMI on `outstanding − amount`. `remainingTenure` counts a final partial instalment as a month and returns `Infinity` if the EMI does not cover the interest. Foreclosure accrues simple daily interest (`bps / 36500`) from the last due date, the charge is on principal, and GST is 18% of the charge. Penal charge is simple daily interest rounded to the rupee.
- **Why:** These functions are the source of truth for every figure the AI states, so each rounding step is explicit and deterministic.
- **Trade-off:** Paise-level rounding can differ by a rupee or two from a rupee-level hand calculation, so tests use a ±₹2 tolerance for lifetime-interest figures.

## D-031 — Policy clauses are data; versions chosen by a per-clause date rule
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Clauses live in `CLAUSES` with numeric `params` (paise and percentages, charges excluding GST) and string `lists` (failure codes). Evaluators read every figure from the selected clause, so cited text and computed numbers come from one record. Each clause declares `versionBy: 'sanctionDate' | 'eventDate'`; PRE-02 uses `sanctionDate` (v2 applies to loans sanctioned from 2026-04-01), the rest use the event date. Selection filters by topic, `appliesTo` and effective window, then prefers the most `appliesTo` constraints, then the latest version, and throws if nothing matches. Loan age is `monthsBetween(sanctionDate, onDate)`. BC-01 stores base ₹500 and GST 18% and computes ₹590. A failure code not listed as chargeable is treated as not chargeable. Foreclosure for loans outside FC-01 (e.g. floating) has no lock-in and uses the prepayment charge.
- **Why:** Rule changes become new clause versions rather than code edits, and the AI can cite the exact clause id and version it relied on.
- **Rejected:** Branching on clause id inside evaluators for the version date; hard-coding numbers in evaluators.

## D-032 — Synthetic dataset derived from domain calculators, reset modelled as a re-amortised tail
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `buildDataset(today)` is pure: schedules come from `amortise`, payments from the schedule (one record per instalment due on or before `today`; a failed attempt gets a failure record plus a `-R` retry success). Rahul's reset leaves the 2026-09-05 instalment at the old rate and EMI; the outstanding after it is re-amortised at 910 bps over `240 − 41` months with `emi(...)` from 2026-10-05, and the schedule is the old rows followed by the new ones. `outstanding` is the closing balance of the last paid row, `nextDueDate` is the earliest unpaid instalment (so Arjun's is overdue), and `lastPaidDueDate` is the last instalment actually paid. Priya's INSUFFICIENT_FUNDS bounce charge comes from `bounceRule`; the BANK_TECHNICAL_FAILURE one is a hard-coded ₹590 that contradicts policy on purpose (the dispute story).
- **Why:** Every figure the AI states must be reproducible from the calculators, and the demo stories need data that deliberately disagrees with policy only where intended.

## D-033 — Mock systems: one tagged chaos hook, seeded PRNG, hang by hijack
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Each route carries `config.system` (crm|lms|payments|policy|ops) and a single Fastify `onRequest` hook applies that system's latency (uniform in its base range plus `extraLatencyMs`), failure (503 `{error:'unavailable'}`) and hang. Admin routes are untagged and exempt. Draws come from mulberry32 when `seed` is given (`Math.random` otherwise), always latency then failure, so a seed reproduces the sequence. `hang` hijacks the reply and tracks the raw response; `onClose` destroys them so `app.close()` and tests never block. Runtime overrides layer over the base profile and `POST /admin/reset` clears them along with the dataset, requests and idempotency map. `x-mock-latency-ms` is set on every response.
- **Why:** Failure behaviour lives in one place, so the AI server's resilience can be tested against realistic, repeatable faults.
- **Rejected:** Per-route sleeps (easy to forget on a new route); letting hung requests dangle until process exit.

## D-034 — Mock idempotency and ops request shape
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `POST /ops/requests` and `POST /payments/links` require `Idempotency-Key` (400 otherwise). The key is scoped per endpoint and fingerprinted by the JSON body: same key and body replays the original body with 200 and `x-idempotent-replay: true`; same key with a different body is 409. First creation returns 201. Ops requests are stored as `{id: 'SR-<6 digits>', customerId, type, params, status:'open', createdAt}` in the server's own map (sequential ids, reset on `/admin/reset`). Mocks do not check customer ownership; the AI server enforces scoping.
- **Why:** The server's retry logic must be safe against a backend that executes at most once per key.

## D-035 — Resilient client: per-attempt abort, p95 hedging with lifetime budget, stale fallback, one-trial breaker
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Every attempt (and hedge) has its own AbortController linked to the caller's signal and its timeout; the first terminal result wins and aborts the rest, and a caller abort rejects with AbortError (no retry, no stale, no breaker count). 2xx is ok, 404 is `not_found` (no retry), 408/429/5xx/network/timeout are retryable and count toward the breaker, and other 4xx is non-retryable `unavailable` that doesn't count. Any answered non-failure response resets the breaker. Retries use backoff `100ms × 2^n` plus jitter; only GETs and POSTs with an idempotency key (sent as `Idempotency-Key`) retry, and POSTs are never hedged. Hedges fire after the rolling p95 of the last 50 successful attempts (400 ms until 20 samples), GET only, one per attempt. The budget uses lifetime counters (hedge n needs n ≤ 10% of GETs, the first is always allowed). After the cooldown the breaker admits a single trial request (no retries or hedge): success closes it, failure re-opens it. When retries run out or the breaker is open, a GET falls back to the last good value within `staleTtlMs` as `{stale:{asOf}}`, observed as 'stale'. Cache key is `ctx.cacheKey ?? path`.
- **Why:** The AI turn has a hard time budget; hedging trims tail latency, stale data with an explicit "as of" keeps answers useful through outages, and writes stay safe because duplicates are only possible behind idempotency keys.
- **Rejected:** Rolling-window hedge ratio (more state, same effect for a PoC); serving fresh cache without calling the backend (this is a fallback, not a cache layer).

## D-036 — Connectors unwrap envelopes and use customer/loan-scoped cache keys; snapshot is partial-tolerant
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `buildConnectors(transport)` returns one `ResilientClient` per system and unwraps the mock envelopes (`{loans}`, `{payments}`, …) so every method returns `Fetched<inner payload>`. DTO types are local (`connectors/types.ts`); the server never imports the mocks at runtime (`@app/mock-systems` is a devDependency for tests and `injectTransport` only). ## D-037 — Redaction by key name, telemetry rolling windows, synchronous per-session JSONL log
- **Date:** 2026-10-25 · **Status:** Accepted

## D-038 — Tool framework: zod schemas, throw-based failures, inlined Gemini declarations, domain-only policy
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Tools declare zod v3 schemas; `ToolRegistry.declarations()` runs `zod-to-json-schema` (no `$ref`) and strips `$schema`, `additionalProperties` and `definitions`, so Gemini gets a plain `{type:'object', properties, required}`. `run()` validates (`invalid` with the zod issues), wraps each call in a `tool:<name>` span, and maps any unexpected exception to `{unavailable, 'internal error'}` with the error text in the (redacted) span attrs. Inside tools, `Gather.need()` throws a `ToolFailure` (naming the failed system) so combined tools stay linear, and records the oldest `stale.asOf` of all fetches. `resolveLoan` always checks the id against the customer's own loan list (cached, stale-tolerant), sets `entities.activeLoanId`, and returns `forbidden` / `ambiguous` (with options) instead of guessing. Rule evaluation uses `@app/domain` (`prepaymentRule`, `foreclosureRule`, `bounceRule`, ...; D-017), but clause citations (id, version, title, text) come from the Policy service, fetched in parallel with the tool's other fetches. If the service fails, the local clause is cited with detail suffix ` (local policy copy)` and a `policy_fallback` span (not an error); if the service's version or text differs from the domain selection, the service text is cited and a `policy_mismatch` span is recorded. `get_service_requests` returns only `id,type,status,createdAt`. `explain_emi_change` takes the cause from the EMI change record (`unknown` if unrecognised), adds `emi_change.direction` (increase|decrease), and takes old/new rate from the latest rate-history entry effective on or before the EMI change date (rate keys omitted if none). `simulate_prepayment.amount` is declared as a string (numbers are stringified by a zod preprocess) because Gemini schemas cannot express `number|string`; `parseAmount` is the only parser. Foreclosure totals are omitted while the loan is inside its lock-in. A bounce charge is "valid" when none was levied, or when the code is customer-attributable and the amount equals the policy amount.
- **Why:** Every figure must trace to a domain function and a cited source, and a single backend outage must degrade one tool honestly rather than fail the turn.
- **Rejected:** Letting the model pass a customer or loan id unchecked; reading rule parameters from the policy service at calc time (a second failure mode for no accuracy gain).

## D-039 — Streaming placeholder renderer and numeric check on LLM-authored segments only
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `PlaceholderRenderer` accepts `{{key}}` where key matches `[a-z0-9_]+(\.[A-Za-z0-9_-]+)+` (spaces inside braces allowed). It holds back only a trailing fragment that could still become a placeholder (`{`, `{{`, `{{emi_ch`, capped at 80 chars); anything that cannot become one is emitted literally at once, and an unterminated `{{` at `end()` is literal, not "unresolved". Values come from a getter at render time. Unresolved keys render `[unverified]` (text) or "a figure I couldn't verify" (voice) and are listed in `unresolved`. The renderer records `segments()` (`{text, bound}`), and `numericCheck(segments, allowed, channel)` inspects unbound segments only. It extracts ₹/Rs/INR/"rupees" amounts, percentages and plain numbers >= 100, skipping ordinals, list numbering, IDs like `PL-71230`, ISO dates and years next to a month name. Amounts must match a money value (exact or whole-rupee), percentages a pct value, and plain numbers any money/pct/months/count value. Spoken-word numbers written by the LLM are out of scope (digits only).
- **Why:** Mid-stream substitution needs minimal hold-back for latency, and checking only LLM text avoids flagging our own bound figures.
- **Trade-off:** A figure with a wrong unit but a right magnitude (e.g. 300 as months vs days) passes the plain-number check.

## D-040 — Actions: propose-only LLM, hash-bound confirmation, execute-time revalidation, idempotent and audited
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The LLM only gets `propose_<type>` tools (kind `propose`); there is no execute tool. A proposal stores the handler-normalised params (amount already in paise) and the figures from `validate`, and is bound to `termsHash = sha256(canonical JSON {type, params, figures}).slice(0,16)` (keys sorted recursively; figures are the `BoundValue` objects). `ActionService.confirm` checks in order: proposal exists and belongs to the session and customer (else `rejected/not_found`, identical for unknown and foreign ids); already `executed` returns the original reference with no second execution; an in-flight execution is joined (same promise) when the hash matches; terminal states reply as such; expired (lazy, audited `expired`); hash mismatch (`rejected/hash_mismatch`, proposal stays pending); then `validate` runs again against live data, and if the recomputed hash differs the proposal is closed as `rejected/terms_changed` (customer must see a fresh proposal). Execution passes the proposal id as the Ops idempotency key so the client's retries cannot duplicate; failure after retries sets `failed`. If execution still fails after the client's retries the outcome is uncertain (the backend may have committed and the response been lost), so the proposal goes back to `pending` with the same id, hash and expiry and the reply is `failed/execution_uncertain` ("safe to retry, no duplicate"); a re-confirm reuses the same idempotency key and the backend de-duplicates. A validation outage at confirm likewise leaves the proposal pending (`failed/validation_unavailable`). Audit `proposed` stores type, hash and figures, never the free-text summary, and `redact` now also scrubs PII patterns (emails, PAN, Indian mobiles, 9-18 digit numbers) inside any string. Everything is appended to a redacting 1000-entry `AuditLog` (proposed, confirmed, executed, rejected, failed, cancelled, expired). Handler schemas do the normalisation (`z.transform` parses amounts), so the same zod schema is the tool declaration (input side) and the validator; the tool path skips re-parsing because the registry already did. The prepayment handler reuses `simulate_prepayment` for ownership, minimum amount and figures, and rejects amounts above the outstanding balance. Handlers invalidate the Ops list (and LMS loan caches for prepayments) after a successful create.
- **Why:** The customer's confirmation is the only authority to act, and it must apply to exactly the numbers they saw, even if the model, the backend or a retry misbehaves.
- **Rejected:** An LLM-callable confirm (prompt-injectable); confirming by proposal id alone (stale terms); re-using the proposal after `terms_changed` (silent price drift).
- **Trade-off:** Proposals live in memory, so a server restart drops pending ones (customer simply asks again).

## D-041 — Provider-neutral LLM interface; Gemini adapter with minimal thinking; prompt ordered stable to volatile
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** The engine talks to `LlmClient.stream(req, signal)` with neutral messages (`user`, `assistant` with `toolCalls`, `tool` results) and chunks (`text`, `tool_calls`, `done` with usage). `GeminiClient` (`@google/genai`, `generateContentStream`) maps tool calls to `functionCall` parts and results to `functionResponse` parts in a user turn, keeps API call ids when present, merges consecutive same-role turns, collects parallel calls and emits one `tool_calls` chunk at stream end, and drops thought parts. `jsonSchema` becomes `responseMimeType: application/json` plus `responseJsonSchema` (guard classifier). Thinking is chosen per model family by `thinkingFor(model)`: 2.5 models get `thinkingBudget: 0` (2.5-pro cannot disable, so 128), 3.x models get `thinkingLevel: LOW` (`gemini-3.8-flash` rejects MINIMAL), other models keep their default; `GEMINI_THINKING` (minimal, low, medium, high, off or a token budget) overrides and defaults to unset. The only fallback is one retry, logged, on an HTTP 400 whose message mentions thinking (MINIMAL falls back to LOW, anything else to the model default). Gemini 3 `thoughtSignature`s on `functionCall` parts are captured into `ToolCall.thoughtSignature` and replayed unchanged on assistant tool calls (a real-API tool round trip is smoke-tested). The `done` chunk carries `finishReason` and `blocked` (prompt block reason, or a SAFETY/PROHIBITED_CONTENT/BLOCKLIST/SPII/IMAGE_SAFETY finish) so the engine can tell a refusal from an empty answer. `checkModels(client, names)` returns configured models the API does not list; `main.ts` calls it once at startup and logs a warning (no import-time side effects). `StubLlm` picks a rule by regex on the last user text and its step is the number of tool round trips since that message (a new user message restarts it); unmatched text gets a fixed reply; an optional per-chunk delay supports load tests. `Limiter` is a FIFO semaphore whose waiters time out (`LimiterTimeout`) or abort independently.
- **Prompt:** `buildPrompt` orders the system text platform rules, workflow prompt, policy summaries (clause ids and titles only), then snapshot, entity memory and channel style, so the first three sections are byte-identical across turns, customers and channels; `prefixHash` (sha256 of those three) tracks cache-prefix stability. The snapshot shows figures only as `{{snapshot.<loanId>.<field>}}` placeholders (values from `snapshotValues`), so no raw figure, PAN or phone enters the prompt and the same renderer and numeric check apply. History keeps the last 12 entries; older ones collapse into one deterministic "Earlier in this conversation: discussed ..." line built from tool names. Replayed tool history is a synthetic call/result pair whose text is wrapped in `<untrusted_data>`; `wrapUntrusted` replaces every `<` and `>` in the payload with `‹` `›`, so no closing tag can be formed however it is split, spaced or nested.
- **Why:** Implicit/explicit context caching only helps if the prefix is identical; a neutral interface keeps the stub and the guard classifier on the same code path; thinking costs seconds on a voice path.
- **Trade-off:** Date-free policy summaries mean clause wording comes from tools, not the prompt. Text-part thought signatures are not replayed (only function-call ones are required).

## D-042 — Engine turn loop: budget-first scheduling, held proposals, guard gate, per-round limiter slot
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `Engine.runTurn` aborts the session's previous turn and waits (max 1 s) for it to record its partial history (`interruptedAt`) before starting, so history order matches turn order. Each LLM round holds one `Limiter` slot for the whole stream (`LimiterTimeout` → fixed "high demand" message, `degraded`). A single budget timer (`TURN_BUDGET_MS`, default 9000) aborts the LLM round; text already streamed stays and a short "shall I raise a ticket?" note is appended (`degraded`). Tools in a round run with `Promise.allSettled`; each tool's timeout is `min(4000, remaining − 1500)` so a hung backend can never eat the time the final answer needs; once remaining < 1500 ms (or after 4 tool rounds) pending calls get `{error:'time_budget_exceeded'|'tool_limit_reached'}` and the model gets one more round, after which further tool requests end the turn `degraded`. Barge-in does not cancel in-flight backend reads (only tool timeouts do), but late results are ignored, and a proposal created by a late or lost `propose_*` result is cancelled immediately. Proposals are held and emitted (after the deltas, before `done`) only on an `allow` verdict; a guard block retracts the text with the refusal, cancels held proposals (audit `cancelled`) and adds a strike; no verdict within `min(1500, remaining)` lets the text stand but cancels proposals (trace guard verdict `timeout`). Blocked LLM output (`done.blocked`) is retracted with a safe fallback, `blocked`, no strike. A guard-blocked input never re-enters the prompt: history stores `[message withheld by safety check]` plus the refusal, the turn's tool entries are dropped and its entity changes are rolled back (prevents a two-step bypass via replayed history). A turn that ends early (barge-in or an unexpected error) waits up to 800 ms for the guard verdict before committing its input to history. When the guard gives no verdict and a proposal is dropped, a short note tells the customer to ask again. Any unexpected exception ends the turn with an apology plus a ticket offer via `delta`/`done`, a `trace` and status `degraded`; the sink is never called after abort; proposal cancellations never reject unhandled (failures are traced). Tool results go back to the LLM redacted, with every whitespace-containing string from `data` wrapped by `wrapUntrusted`, values as `"{{key}} = display"` and source refs only; failures as `{error, message, options?, values?}`. The per-turn value map is snapshot + entity + all tool values (including failure values) and feeds the renderer via a getter. History stores tool entries as name + compact summary without figures, so figures in a later turn always come from a fresh tool call. Backend calls are logged for replay through a new `TurnTracer.onCall` listener; `CallEvent` gained `method` and `path`. `Guard`/`GuardVerdict`/`RefusalFn` live in `platform/guard/types.ts` for Task 15.
- **Why:** Review Focus 2 (a backend slower than the turn) must still produce an honest answer within budget; proposals must never reach the customer unless the input passed the guard.
- **Trade-off:** Real Gemini latency (about 2–5 s per round with thinking LOW) means a two-round turn sometimes reaches the 9 s budget; the answer is then cut with the fallback note rather than allowed to run long.

## D-043 — Malicious-input guard: sync rules, then a small-model classifier; fail-open with proposals dropped
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** `Guard.check` runs `rules(text, ctx)` synchronously (case-insensitive, word-boundary regexes) and returns on a hit (`by:'rules'`, 0 ms). Otherwise `llm.stream` runs the guard model (`GEMINI_GUARD_MODEL`) at temperature 0 with a `{verdict, category}` JSON schema; the system prompt defines the six categories in one line each and says ordinary requests (complaints, frustration, waiver requests, policy questions) are allowed; the customer text goes in `wrapUntrusted`. Rule categories (current): injection (ignore/disregard instructions, "you are now", developer mode), prompt_extraction ("system prompt/instructions", a reveal/print/repeat/leak/dump/output verb plus "your ... instructions/prompt/rules", or "your system/hidden/initial/internal/secret prompt/instructions"), impersonation (act as admin/bank/manager; "I am from the bank/Northstar/RBI"; "I'm a bank officer/employee/staff" or "<role> at/of/from <bank>"; waive plus a first-person "I'm authorised"), coercion (waive plus "I have authorisation" or "manager/supervisor/officer/admin/head/RBI approved/authorised"), cross_customer (a loan ID `HL|PL|TW` + 5 digits, with dash, space or no separator, not in `ownedLoanIds`; another customer's full name or first+last; and any 9–18 digit number right after "account"/"acct"/"a/c", with an optional "no/number/num/#/:" and no separator needed, since the context holds no account numbers). Before matching, the first 2,000 chars are NFKC-normalised, stripped of `\p{Cf}` format characters, and curly quotes are mapped to ASCII. A plain "can you waive my late fee?" is allowed: the agent can raise a ticket. A first name alone is not blocked (too many false positives); the classifier covers it. Unparseable classifier output allows with `by:'model'` and is logged; an abort or timeout allows with `by:'timeout'`, and a classifier error (network, quota) is also reported as `timeout`, so the engine drops proposals rather than trusting an unscreened turn. The guard never throws and also races the passed signal, so a client that ignores abort cannot hang the turn.
- **Engine wiring:** `GuardContext` gained `ownedLoanIds` (from the session snapshot) and the engine takes `demoCustomerNames` (the current customer's name is filtered out). `refusalFor(category, strikes)` is the engine's default refusal: category-specific polite text, plus an offer to connect a team member from strike 2. From the second strike a block appends `{event:'guard_escalation', detail:{turnId, category, by, strikes}}` to the optional `audit` dep's `AuditLog`.
- **Why:** Rules catch the obvious cases for free and instantly; the model catches paraphrases. The rules deliberately avoid blocking benign servicing language, because a false block is a worse customer experience than a missed low-risk probe, and the other defences (tools never take a customerId, propose-only, hash-confirmed actions) hold regardless.
- **Trade-off:** Real `gemini-3.5-flash-lite` classification takes about 1.0–1.4 s, inside the engine's guard wait but not free; the customer's own account number in a message is blocked as cross_customer.
- **Rule narrowing (fix round 1):** rules must not fire on ordinary customer language. `prompt_extraction` needs `system prompt/instructions`, a reveal/print/repeat/leak/dump/output verb plus "your ... instructions/prompt/rules", or "your system/hidden/initial/internal/secret prompt/instructions"; "share your guidelines" and "tell me your rules" go to the classifier. Waive-plus-authority needs a first-person claim ("I'm authorised", "I have authorisation") or "manager/supervisor/officer/admin/head/RBI approved"; "autopay authorised by me" and "approval from the bank" pass. `i_am_staff` needs a bank context ("I am from the bank/Northstar/RBI", "bank officer/employee/staff", "<role> at/of/from <bank>"); "I am a manager at Infosys" passes. Before matching, input is capped at 2,000 chars (the classifier still sees all of it), NFKC-normalised and stripped of `\p{Cf}` format characters (zero-width splitting). Loan IDs accept `-`, a space or no separator and are normalised before the ownership check. The account-number regex has no adjacent unbounded `\s*` groups, so large whitespace input stays linear. Trade-off: padding more than 2,000 chars before an attack hides it from the rules, not from the classifier.
- **Fix round 2:** curly apostrophes/quotes (iOS smart punctuation) are mapped to ASCII during normalisation, so `I’m ...` patterns match; the account-number pattern accepts `accountno5010...`, `acct5010...` and `a/c3162...` while staying free of adjacent unbounded groups.

## D-045 — Gateway: stateless HMAC tokens, one socket per session, resume window, rate limits
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** A token is `base64url(json{customerId, sessionId, exp}).base64url(HMAC-SHA256)`, expiring after 12 h, verified in constant time; `/api/login` (OTP `123456`, optional `DEMO_ACCESS_CODE`, 10 per minute per IP, 429 beyond) creates the `sessionId`, while the `Session` object is created on first WebSocket connect. The WebSocket is a raw `ws` server (`noServer`, 64 KB max payload) on the Fastify HTTP server, authenticated at upgrade (401 before any WebSocket exists). A reconnect within 5 minutes of `lastSeenAt` resumes the same session and history (`resumed: true`); an older session with the same id is replaced by a fresh one. Only one socket per session: a newer connection closes the older with code 4001 and abandons its running turn, and a closing active socket aborts its turn (otherwise the answer would stream to nobody). `lastSeenAt` is touched on every message, on disconnect, and by the 60 s sweep for sockets that are still open, before sessions idle for 30 minutes are deleted. User turns are limited to 30 per minute per session (`rate_limited` error, turn not run). `confirm_action` runs `ActionService.confirm` with the session's own customer, so a token for another customer gets the same `rejected` as an unknown id; after `executed` the ops list, the customer's loan list and the affected loan's detail, schedule and payment caches are invalidated, the snapshot reloaded and pushed. A cancelled or closed proposal is reported as `rejected` because the wire protocol has no `cancelled` status. `/api/chaos` validates PUT bodies (known systems, `extraLatencyMs` 0-10000, `failRate` 0-1, boolean `hang`, no extra fields) before proxying to the mock admin; `/api/chaos/reset` also clears the connector fallback caches. CORS allows `http://localhost:5173` plus the comma-separated `WEB_ORIGIN`, implemented as a small hook rather than a dependency. Config is one typed object (`loadConfig`), reading the repo-root `.env` through `process.loadEnvFile` (guarded, real env wins), failing fast without `GEMINI_API_KEY` for the gemini provider, and generating a random `SESSION_SECRET` with a warning when unset. `LLM_PROVIDER=stub` uses `StubLlm` with a small rule set and a classifier stub that always allows (the guard rules still run).
- **Why:** Stateless tokens need no store and survive nothing they should not; the server remains the only authority on which customer a socket belongs to (no customer id is ever read from a client message).
- **Rejected:** `@fastify/websocket` and `@fastify/cors` (extra dependencies for little); trusting `X-Forwarded-For` for the login limit (spoofable when the server is exposed directly, so the limit keys on the socket address).
- **Trade-off:** Behind a reverse proxy all logins share one IP and one bucket until `trustProxy` is enabled. History shown after a resume has no source chips (only text is kept in the session). `/api/chaos` and `/api/metrics` are unauthenticated, as specified, so they should not be exposed publicly without a gateway rule.

## D-047 — Value semantics over prompt cleverness
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:** Ambiguity that produced misleading answers is fixed in the bound values, not by prompting harder. Failed payments expose `bounce_charge_levied`, `bounce_charge_due`, `refundable` (`max(levied - due, 0)`), `disputable` (`yes` iff refundable > 0), `failure_reason` and `date`, plus `payments.total_refundable`, keyed by a newest-first ordinal alias (`payments.failed_1.*`) as well as by payment id. Tool data returned to the model carries the payment id only in `ref` (internal), and `propose_dispute` accepts the alias or a real id. The alias is resolved at propose time and the real payment id is stored in the proposal params (a validate result may return normalised `params`), and the payment date is a bound figure, so the terms hash binds to that specific payment; execute uses only the stored id, and validate (at propose and again at confirm) fails closed if the payment is gone or no longer qualifies. Validate also enforces policy server-side: the disputed amount is `refundable = levied - due` (via `bounceRule`), and a charge with nothing refundable is rejected citing the clause. Customer-facing `text` values are humanised at the source (EMI cause enums become sentences), `formatBound` turns any remaining snake_case `text` into spaced words, and the renderer drops a duplicated "months" after a bound months value. `check_foreclosure` adds `penalty_free`, `penalty_amount` (charge + GST, only when foreclosure is allowed) and, in the lock-in case, `blocked_reason` next to `lock_in_ends_on`; the prompt rule only cites keys that exist for the case. The platform rules add: units come with placeholders, no raw enum names, no internal reference IDs (refer to payments by date), and answer the condition of a yes/no question literally first.
- **Why:** Live runs were figure-bound yet wrong: a valid-looking pair (`bounce_charge`, `bounce_charge_valid`) was misread, so the model called a levied charge "not valid" and offered to dispute the valid one. A value that names exactly what it means leaves nothing to misread.
- **Rejected:** More prompt text explaining the old pair; post-hoc answer rewriting.
- **Trade-off:** `failed_N` is positional (newest first over all of the customer's loans, via one shared helper used by both the history tool and the dispute action), so it is only stable while the failed-payment list does not change between the model's read and the proposal; the id and date frozen into the proposal remove the risk after that point.

## D-048 — Voice turn manager: warm TTS pool, energy + transcript barge-in, self-echo guard, deterministic voice confirm
- **Date:** 2026-10-25 · **Status:** Accepted
- **Decision:**
  - **One `VoiceSession` per WebSocket in voice mode** (`platform/voice/turnManager.ts`). The Scribe realtime STT socket opens on `voice_start` and stays open (VAD commits, `STT_SILENCE_SECS`; `voice_start {mode:'ptt'}` uses manual commits sent on `ptt {down:false}`, and mic audio is forwarded only while the button is held). Domain key terms (EMI, foreclosure, NACH, lakh, …) are passed as `keyterms`. A committed transcript is the only thing that starts an LLM turn (D-014, no speculative start). Each spoken reply is an *utterance* with its own `turnSeq` (the engine's seq for engine turns) that tags every binary frame, with `tts_begin`/`tts_end` around it.
  - **TTS pool (one warm socket), one socket per utterance.** `TtsPool` keeps one pre-opened ElevenLabs stream-input socket; `take()` hands it out and opens the next in the background, and sockets older than 150 s are recycled (the vendor's inactivity timeout is 180 s). A socket serves exactly one utterance (filler + answer + read-back), then gets end-of-input (`{text:''}`); on barge-in it is closed at once without a flush. Rejected: one long-lived socket per session (a barge-in must discard queued audio, which needs a close anyway) and a socket per turn opened on demand (~170 ms connect + handshake on every first audio).
  - **Text to speech:** engine voice-channel deltas (already speech-formatted bound values, D-015) are mirrored to the client as `assistant_delta` and cut by `ClauseChunker` (at `.?!;:`+space, at a comma once 40+ chars, or at a word boundary by 120 chars). The first clause, fillers and read-backs are sent with `flush`, because the 50-char first step of the chunk schedule would otherwise hold a short first sentence back. A proposal is read back as `summary` (display rupees rewritten with `speakInr`) + "Shall I go ahead?".
  - **Barge-in** only while assistant audio is in flight: from the first frame until the estimated client playback end (bytes sent ÷ 48 per ms + 300 ms after the first frame), or until a `playback_report` says it finished. Triggers: (1) energy VAD on the raw mic PCM, ≥ `BARGE_IN_VAD_MS` (500) of frames above `max(BARGE_IN_VAD_DB` (-40 dBFS), noise floor + `BARGE_IN_VAD_MARGIN_DB` (15)), with dips under 150 ms counted as voiced; voiced time accumulates only while our audio is in flight (reset otherwise), and the noise floor is an EMA over every frame (~3 s rising, ~0.3 s falling) so steady fan or street noise is learnt. If no non-filler words (partial or committed) follow an energy barge-in within 2.5 s, `voice_barge_in_unconfirmed` is recorded and the assistant says "Sorry, go ahead." rather than stay silent; (2) a partial with ≥ `BARGE_IN_MIN_WORDS` (2) non-filler words; (3) a keyword (stop, wait, hold on, ruko, one second, actually); (4) a 1-word partial that has lasted 400 ms; (5) pressing push-to-talk. Lone fillers (um, uh, hmm, ok) never count. Barge-in aborts the engine turn if it is this utterance's, closes the TTS socket, sends `barge_in`, and never touches pending proposals. The new utterance becomes the next turn when its transcript commits. Any committed new input while an utterance is still thinking or talking ends that utterance the same way.
  - **Heard text:** TTS alignment is accumulated per utterance; on `playback_report(turnSeq, playedMs)` (or an estimate after 1.5 s) the characters starting at or before `playedMs` become `interruptedAt` on that turn's assistant history entry. `interruptedAt` now means "what the customer got" everywhere (the engine's own abort path stores the streamed text), and the prompt replays an interrupted answer as `<heard>… [customer interrupted here]`.
  - **Self-echo guard:** in open-mic mode a partial or committed transcript is dropped when it began while our audio was in flight and ≥ 70% of its words appear in the last 200 characters sent to TTS. It protects mainly against the assistant's own "Shall I go ahead?" being transcribed and taken as consent.
  - **Voice confirm is deterministic, never the LLM, and only for what was heard (D-021):** the session keeps `awaitingConfirmation {proposalId, termsHash}`, armed only when **playback** (at least one audio frame; a read-back that produced no audio never arms) of the read-back of a proposal surfaced through the engine's proposal sink has ended — the read-back was generated in full (TTS final), was the last thing in that utterance and was not barged in on, and then either the client's `playback_report` shows that utterance played to the end or the `playbackEndsAt` estimate (audio length + margin after the first frame) passes, whichever is first. A yes whose speech began (first partial, or the onset of the latest mic voice run, tracked on every frame even with `BARGE_IN_VAD_MS=0`) before consent was armed is treated as not heard and gets a re-read. `awaitingConfirmation` is cleared by any barge-in, any new utterance (engine turn, filler prompt, outcome), a typed `user_text` turn, an opener or `set_workflow`, voice_stop, and the proposal being resolved elsewhere (UI confirm/cancel, expiry; checked against `pending()` at use). The re-read speaks the surfaced view's terms and is skipped (normal engine turn) if its `termsHash` no longer matches the pending proposal. A committed whole-utterance affirmation (fixed set, e.g. "yes", "go ahead", "haan ji"; "yes but…" is not) confirms only the awaited proposal through the gateway's own confirm path (`ActionService.confirm(..., 'voice')` with the stored `termsHash`, `action_result`, snapshot refresh) and says "Done — your reference is SR 4 8 2 1 0 0."; a negation cancels it ("Okay, I've cancelled that."). With nothing awaited but exactly one surfaced proposal still pending, "yes" gets a re-read ("Just to confirm: <summary> Shall I go ahead?"), which awaits consent once heard, and "no" cancels. Proposals held inside a running turn (not yet surfaced or guard-cleared) are never acted on; yes/no then is a normal engine turn. Voice confirm, cancel and re-read log a `user_input` event (redacted by the event log).
  - **Fillers:** on a tool `progress`, if no text has gone to TTS and no audio has gone out `FILLER_AFTER_MS` (700) after the commit, the tool's filler is spoken once per turn.
  - **Telemetry:** voice spans (`stt_commit`, `filler`, `tts_first_audio`, `barge_in`) and metrics (`voice_stt_commit_ms`, `voice_turn_e2e_server_ms`) are merged into the engine's `TurnTrace` before it is sent (held up to 3 s for the first audio), so the existing waterfall shows them; spans are relative to the commit, which is the engine turn's start. Process metrics: `voice_stt_commit_ms`, `voice_first_audio_ms`, `voice_turn_e2e_server_ms`, `voice_tts_first_audio_ms`, `voice_barge_in_audio_ms`, client-reported `voice_e2e_ms` (`client_mark` speech_end → first_audio_played).
  - **Failures:** an STT socket failure reconnects once (silently); a second failure sends `error voice_vendor_error` once, stops the session (STT, TTS pool) and frees its voice slot. A vendor's clean session end (close 1000/1001, time limit, inactivity) is not counted as a failure: it reconnects on the next audio or PTT press (1 s of audio is buffered meanwhile), and a PTT release during the reconnect is queued and committed once connected. In PTT mode a silent 20 ms frame every 5 s keeps the STT session from idling out (vendor-agnostic; `keepalive_interval_ms` was not relied on). A closed `TtsPool` rejects `take()`, so nothing opens a TTS socket after `voice_stop`. A TTS failure sends `voice_vendor_error` and `tts_end`; the text answer still streams. `MAX_VOICE_SESSIONS` is enforced in the gateway (`voice_capacity`), the slot reserved before the vendor handshake. Outbound audio is dropped when more than 2 MB is buffered for a slow client.
- **Why:** Measured on the real vendors, Scribe partial transcripts lag speech by 1.5–2 s whatever the chunk size, so transcript-only barge-in reacted in 1.2–1.6 s; at 400 ms the energy trigger fired 0.4 s into the interruption; the reviewed 500 ms default fired at 1.3 s on the fast synthetic fixture (its "Actually," is 440 ms, then a pause) and is expected to catch a natural spoken interjection. The echo guard and the fixed affirmation set make "yes" safe on a laptop speaker without a model in the loop.
- **Trade-off:** the energy trigger reacts to any loud enough voice, including a reviewer's voice leaking from the call if the browser's echo cancellation misses it; `BARGE_IN_VAD_MS=0` falls back to transcript triggers and push-to-talk remains the safety net. Within the echo window a user who answers with exactly the assistant's words ("go ahead" right after "Shall I go ahead?") is ignored; "yes" works. ElevenLabs reports alignment times cumulatively across chunks (the docs say per chunk); the code accepts both.

## D-049 — Browser voice: worklet capture, queue-behind playback, client-owned voice state
- **Date:** 2026-10-26 · **Status:** Accepted
- **Decision:**
  - **Capture:** `getUserMedia` with echo cancellation, noise suppression and AGC on, mono, into an `AudioWorklet` (`capture-worklet.js`, served as a real asset: Vite's `assetsInlineLimit` is switched off for it, since a data: URL module is fragile). It runs at the context's native rate and uses an averaging decimator to 16 kHz (box filter with a fractional phase, so 44.1 kHz does not drift), emitting 320-sample Int16 frames; the main thread wraps them with `encodeAudioFrame(0, …)`. The decimator is an exported class so it is unit tested without a browser.
  - **Playback:** `PcmPlayer` schedules one `AudioBuffer` per server frame back to back on the AudioContext clock (24 kHz context; the browser resamples if it cannot honour that). 60 ms jitter buffer before the first frame, and again after an underrun. The clock and sources sit behind a `PlayerBackend` interface so the scheduling is tested with a manual clock. A frame with a lower `turnSeq` than the current one is dropped; a **higher turnSeq queues behind audio already scheduled instead of cutting it** (the server sends a short filler utterance and then the answer, and the filler is still playing when the answer's first frames arrive). Only `flush()` (barge-in, stop) cuts audio, and it also blocks the flushed seq so frames still in flight are dropped.
  - **Reports:** `playback_report {turnSeq, playedMs}` is sent once per utterance when its last buffer ends after `tts_end` (the server arms spoken consent for a read-back from this), and on `barge_in` with `playedMs` at flush time. Utterances that produced no audio send nothing. `playedMs` is elapsed audio-clock time since the utterance's first buffer started, capped at its scheduled length.
  - **State:** the voice state (`off / connecting / listening / thinking / speaking`) is owned by the client controller, driven by server messages and the player (speaking begins when the first buffer actually plays, ends when the player reports idle), not by the reducer, because `tts_end` arrives well before the audio is heard. The reducer keeps only the live caption (a final transcript clears it, since `turn_start` already carries the user bubble) and the `interrupted` flag on the assistant message.
  - **Marks:** `speech_end` is taken when the final transcript arrives (epoch ms from `performance.timeOrigin + performance.now()`) but sent when `turn_start` supplies the turnId; `first_audio_played` is taken when the first buffer of a turn starts. The trace tile reads `voice_e2e_ms`, falling back to `voice_first_audio_ms`.
  - **Push-to-talk:** the setting is kept in `localStorage` (try/catch), fixed while a session runs, and sends `voice_start {mode:'ptt'}`. Hold the mic button or Space (ignored while typing in a field or when another button has focus); mic frames are sent only while held. A socket close tears voice down locally (the server's voice session ends with the socket), and logout does the same.
- **Why:** Queue-behind keeps fillers audible without a second player; a client-owned state avoids a "listening" indicator while the answer is still playing; sending frames only while held halves PTT bandwidth and matches what the server forwards anyway.
  - **Fix round 1 (controller state machine):** `VoiceController` takes injected deps (capture, player factory, socket, clock) so the state machine is unit tested. A start-generation token (bumped by every start and teardown) makes a start that is cancelled while the microphone opens stop the late capture and send nothing; `voice_stop` is sent only if `voice_start` was. "Speaking" is set on every utterance's first audible buffer (a filler does not hide the answer's), and an idle report leaves speaking only when no scheduled audio remains. `PcmPlayer.flushAll()` returns one report per utterance that had audio and had not already sent its idle report (a filler with its played ms, the queued answer with 0); on barge-in the controller sends one `playback_report` per entry, and none for utterances already reported or silent. The debug history is capped at 50 entries.

## D-050 — Collections pack: penal charge per instalment, optional amounts defaulted server-side
- **Date:** 2026-10-26 · **Status:** Accepted
- **Decision:** `get_overdue_summary` computes the PEN-01 penal charge per overdue instalment on that instalment's own days past due (the clause says "on the overdue instalment for the days it remains unpaid"), and `overdue.total` is overdue instalments plus that charge. `promise_to_pay` and `payment_link` take an optional `amount` that defaults to the overdue total on the server, because the model cannot write figures (D-015). - **Why:** Per-instalment accrual matches the clause wording and gives a larger charge for the older instalment; server-side defaults keep every figure bound.
