## Where the time goes

Median share of a turn's server time (default run, 70 turns, `gemini-3.5-flash-lite`), computed from the trace spans: LLM rounds 71%, tool execution 29% (tool spans overlap with each other, so their union is used), everything else 0%. The guard classifier (p50 1163 ms, p95 1408 ms) runs in parallel with the turn; the engine waited out its verdict timeout in 0 of 70 default turns.

- **LLM.** First token p50 1348 ms (p95 1755 ms). A tool turn needs two model rounds, so the model is the largest single cost of a 3947 ms median turn.
- **Tools.** Slowest by p50: tool:propose_promise_to_pay 1830 ms (p95 2338); tool:get_payment_history 1735 ms (p95 4005); tool:get_overdue_summary 1117 ms (p95 1402). A tool span includes every backend call it fans out to; backend p50 per system: policy 60 ms, lms 284 ms, payments 627 ms, ops 763 ms.
- **Journeys.** Slowest by median turn: J3 5915 ms, J4 3829 ms, J2 3780 ms, J1 3585 ms.
- **Chaos (`payments:2500:0.3`).** 70 turns, turn_total p50 3615 ms, p95 5687 ms, max 6135 ms against a 9000 ms budget; 0 turns ended degraded and 0 guard verdicts timed out. Payments calls: breaker_open 21, timeout 12. When payments is down the assistant cannot build the dispute or promise, so the journeys did not always reach their confirm step; runs with a proposal to confirm: J2 10 of 10, J3 6 of 10, J4 0 of 10. That is the honest outcome (the answer says it could not check), not a runner fault.
- **Hedging did not fire in any run (honest finding).** Completed hedged attempts: 1 of 318 calls by default and 0 of 272 under chaos. Two mechanisms explain it. (1) A hedge starts only for a GET while the circuit breaker is closed, after the rolling p95 of recent successes, within a 10% budget, and never on a half-open trial. Under `payments:2500:0.3` every payments call exceeds the 1.5 s call timeout, the consecutive-failure count reaches 5 inside the first logical call (3 attempts, each possibly with a hedge), the breaker opens for 10 s, and from then on payments calls are short-circuited or half-open trials. (2) A hedge that loses the race is cancelled before it reports, so this counter only sees hedges that completed, which understates launches. A slow-tail run (`payments:600:0`: every payments call about 600 ms slower, still inside the 1.5 s timeout) gave payments p50 1196 ms / p95 1473 ms and 0 completed hedged attempts in 318 calls: hedging did not help there either, because the hedge delay is the rolling p95 of recent successful calls, so a backend that is uniformly slower moves its own p95 up and no call looks like a tail outlier. Hedging helps against occasional slow outliers on an otherwise fast backend, which these profiles do not produce; the breaker, retries and stale fallback are what handled the outage here.
- **Voice.** End of speech to final transcript p50 1041 ms; LLM first token p50 2050 ms (p95 2623); first audio at the test client p50 3336 ms, p95 3838 ms (5 runs). The STT silence window and vendor commit set the first term; the LLM first token and the first TTS sentence the rest.

## Path to 1,000 concurrent

What the load test shows (stub LLM, one Node process, load generator on the same Mac):

- **Server overhead is small.** 500 sessions with the LLM limit lifted to 1000: turn p50 2313 ms and p95 2519 ms for a turn whose ideal stub time is 1800 ms; 0 failed turns; event-loop lag p99 peak 24.6 ms (the histogram resolution is 20 ms, so this is the floor, not a measured idle value). RSS 107 MB empty, 222 MB with all sessions connected, 321 MB peak: about 236 KB per idle session, so 1,000 sessions is roughly 535 MB at the peak-under-load rate.
- **What degrades first is the LLM concurrency limit (50) with its 4 s queue timeout, by design.** At 200 sessions everything completes (peak queue 116, turn p50 5624 ms). At 500 sessions: peak queue 427, turn p50 9005 ms, and 215 of 2500 turns were answered with the "very high demand" message. Shedding is the intended behaviour, but a 50-wide limit cannot serve 1,000 users.
- **Call-rate arithmetic for 1,000 concurrent users.** If each user sends one turn every 10 s, that is 100 turns/s. A tool turn needs at least two answer-model calls (the tool round and the final answer) plus one guard classification, so about 200 answer calls/s plus 100 guard calls/s, roughly 300 model requests/s. At the observed first-token latency that is hundreds of calls in flight, far above a limit of 50.
- **What breaks next, in order:** (1) the provider quota on the Gemini key (requests and tokens per minute) before our limiter matters; (2) the single event loop: synchronous JSONL appends in the event log (`appendFileSync` per event), JSON serialisation of every delta and trace, and snapshot loads all run on one thread; the lag is not visible at this scale, but it is the first CPU limit; (3) backend fan-out (a cold turn makes 3 to 7 backend calls) and the per-process connector caches; (4) in-memory sessions, proposals and audit log tie a user to one process.
- **What to change:** raise `LLM_MAX_CONCURRENCY` to the provider quota and put the guard on its own limiter so it cannot starve answers; replace `appendFileSync` with a buffered asynchronous writer; run N Node processes behind a load balancer with sticky routing by session id and move sessions, proposals and the audit log to Redis or a database so a reconnect can land anywhere; add a shared cache in front of the read endpoints and keep hedging on; shed load before the model call by queue depth rather than by timeout, and keep voice on a separately capped pool (`MAX_VOICE_SESSIONS`), since each voice session also holds an STT and a TTS websocket to the vendor. The scarce resource is model tokens, not CPU.
